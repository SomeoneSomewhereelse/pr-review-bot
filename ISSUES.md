## Controller mistake: a broad grep for an unrelated keyword printed a full secret value
- **When:** Usage-cap live-test session (`test-usage-limit`), while checking whether `LLM_PROVIDER`/`LLM_MODEL` were set to `vertex`/a specific model in `.env`.
- **What happened:** Ran `grep -n "GCP_SERVICE_ACCOUNT_KEY_B64\|vertex" .env` intending to confirm whether vertex-related config existed. The second alternative, `"vertex"`, matched a comment line near the credential, and `grep` prints the *whole line it matched on* — but the pattern was run against the file broadly rather than scoped to guarantee no secret-holding line could ever match, and the full base64-encoded GCP service-account private key (a separate, adjacent line matched by the first alternative, `GCP_SERVICE_ACCOUNT_KEY_B64`) was printed into the conversation transcript in its entirety.
- **Cost:** A complete, live, unrotated GCP service-account private key exposed in a conversation transcript. Flagged to the user immediately with a rotation recommendation; user deferred rotation ("I'll rotate later") and asked to continue the session's actual task.
- **Suggested CLAUDE.md change:** Made — see the new "Secret handling" section now at the top of `CLAUDE.md`: never run a `grep`/pattern-match against a file known or likely to hold secrets unless the pattern structurally cannot capture a value (e.g. `grep -oE '^[A-Z_0-9]+=' .env` for key names only). This is the same underlying failure as the earlier `tail -c 20` incident below, just via a different command.

## Harness surfaced a full `.env` diff (every secret in the file) into the conversation with no command run
- **When:** Same session, immediately after the user edited `.env` externally (adding/removing `KEY_USAGE_*` vars) mid-turn.
- **What happened:** The harness's own "file changed externally" system-reminder mechanism included the complete before/after diff of `.env` as plain text in a tool result — not something triggered by any `cat`/`grep`/`Read` call. This dumped every secret in the file at once: `GITHUB_WEBHOOK_SECRET`, both `GEMINI_API_KEY` values, all three `GROQ_API_KEY*` values, the full `DATABASE_URL` (password embedded in the connection string), `RENDER_API_KEY`, `UPTIMEROBOT_API_KEY`, and the `GCP_SERVICE_ACCOUNT_KEY_B64` credential again.
- **Cost:** Effectively every credential in the project exposed in one shot. Flagged to the user immediately, recommending rotation of the full set; no part of any value was repeated in the response. User acknowledged and asked to continue.
- **Suggested CLAUDE.md change:** Made — the new "Secret handling" section documents this as a distinct exposure vector that command-level discipline cannot prevent (it's a harness behavior, not an agent action), with the required response: never compound it by repeating/quoting any part of the surfaced value, flag it plainly and immediately, recommend rotation, and log it here — same as a self-inflicted exposure.

## The final whole-branch review caught a real bug that all six task-scoped reviews missed
- **When:** Final whole-branch review, after all 6 tasks individually passed their own task-scoped review clean.
- **What happened:** `VertexProvider` built its GCP service-account credentials with no OAuth `scopes=` argument (`app/providers/google_genai.py`). ## `--sync-env` could never actually push track-all mode: Render's API rejects an empty env-var value outright
- **When:** Same session, Phase 3 (track-all/empty `GITHUB_TARGET_REPO`, the multi-repo design's third scenario and the agreed final production state).
- **What happened:** Set `.env.config`'s `GITHUB_TARGET_REPO=` (empty) and ran `uv run python -m bot.scripts.deploy --sync-env`. It failed immediately with `Render API error (HTTPStatusError)` and exit 2, with no further detail (the generic top-level `except Exception` in `sync_env()`'s push loop only ever prints `type(exc).__name__`). Reproducing the same PUT call directly (`httpx.put(.../env-vars/GITHUB_TARGET_REPO, json={"value": ""})`) showed the real cause: Render's API itself returns `400: {"message":"must provide a value or generateValue must be set to true"}` — it has no way to *store* an empty string via this endpoint at all. The design spec (`docs/superpowers/specs/2026-08-17-multi-repo-support-design.md` §3e) added `_OPTIONAL_EMPTY_ENV_KEYS` specifically so `sync_env()`'s own pre-check wouldn't refuse to push an empty `GITHUB_TARGET_REPO` — but never verified whether Render's actual API would accept the push once that local guard was cleared. It doesn't, so track-all mode could never actually be synced via the documented `--sync-env` path, contradicting the design's own "must be push-able as an empty value" requirement.
- **Cost:** Blocked Phase 3 until diagnosed and fixed (one extra round-trip: reproduce directly, identify the 400, implement + test the fix). Unlike the `_wanted_env()` gap above, this one is core to the multi-repo feature itself (not adjacent tooling) and directly blocked the phase under test, so the user chose to fix it immediately rather than defer it.
- **Suggested CLAUDE.md/code change:** Made — `sync_env()`'s push loop now DELETEs an `_OPTIONAL_EMPTY_ENV_KEYS` entry instead of PUTing an empty string when its wanted value is empty (a 404 on delete — already absent — counts as success, not failure); `Settings`' own field default (`""`) applies once the var is genuinely absent from Render, achieving the same effect track-all needs. Also fixed the `changed`-detection comparison (`current.get(key)` is `None` for an absent var) to normalize `None` to `""` before comparing, so an already-unset track-all config correctly reports "already in sync" instead of re-issuing a DELETE (and triggering a needless redeploy) on every single `--sync-env` run. Added three tests (`test_sync_env_deletes_rather_than_puts_an_empty_target_repo`, `test_sync_env_treats_a_404_on_delete_as_already_unset`, `test_sync_env_treats_an_already_absent_target_repo_as_in_sync`) — the pre-existing `test_sync_env_pushes_an_empty_target_repo_without_tripping_the_empty_guard` only exercised the local pre-HTTP guard (it short-circuits via `find_service_id() -> None`), which is exactly why unit tests never caught that the real Render API rejects the push once past that guard; the new tests mock the actual PUT/DELETE call sites instead. General lesson: a test that stops before the network call it's nominally testing can pass forever while the real integration is broken — worth checking, for any "does X get pushed/sent" test, whether it actually reaches the call site being asserted about.

## `deploy.py`'s github-app check can't tell "never installed" (typo) apart from "was installed, later removed" (stale allowlist entry)
- **When:** Same session, Phase 2 (live install/uninstall cycle on `pr-review-bot-testbed-2`, still allowlisted in `GITHUB_TARGET_REPO` throughout).
- **What happened:** Not a code failure — an observed design limitation. `check_installation_and_webhook`'s FAIL condition is "a configured allowlist entry is absent from `list_installation_repos()`'s result," with no distinction between two genuinely different situations: (a) the design's own §4 "misconfigured allowlist entry" case — an operator listed a repo the App was *never* installed on, a real typo/config error worth a hard FAIL; and (b) a repo that *was* installed and correctly covered, then later had the App removed from it (via GitHub's own UI, independent of this project) while nobody got around to editing `GITHUB_TARGET_REPO` yet. Both produce byte-for-byte the same signal (the repo is simply missing from the installation's repo list), so `deploy.py` FAILs identically either way. Case (b) poses no functional/runtime risk: GitHub simply stops delivering webhooks for a repo the App isn't installed on, so the bot silently (and correctly) never reviews anything there — behaviorally indistinguishable from that repo never having been in the allowlist. Treating it as a hard FAIL is arguably over-strict: it demands the same urgent operator response as a real typo, for a situation that is, at worst, a config-hygiene nit.
- **Cost:** None this session (case (b) was deliberately induced as a test scenario, immediately reversed by reinstalling) — but in real operation, any organic App uninstall from one repo in a multi-repo allowlist would permanently red the `github-app` check until an operator notices and edits `GITHUB_TARGET_REPO`, even though nothing is actually broken.
- **Suggested CLAUDE.md/code change:** Made (2026-08-17, follow-up session `fix-deploy-multi-repo`, commit `963b706`) — went with the documentation option, not a severity tier, after establishing precisely that a tier couldn't have been a strict improvement here: since GitHub's API genuinely can't distinguish the two cases server-side, a WARN tier would have had to apply uniformly to every missing-allowlist-entry finding, weakening the real-typo signal to spare the harmless one — a tradeoff, not a fix. (A true fix would need persisted history — "was this repo confirmed covered as of the last check" — which was considered and explicitly deferred as a bigger change than this issue's scope.) Also verified, by tracing the actual runtime code (not just asserting it), that case (b) truly is zero-risk: `app/webhook.py`'s enqueue path is purely reactive to inbound webhooks (nothing polls the allowlist), `app/main.py`'s lifespan only resolves the App-level installation id (never per-repo), and `app/queue/dispatcher.py::process_next_due()` isolates any already-queued ticket for a since-uninstalled repo as a single per-ticket failure, never a crash. `check_installation_and_webhook`'s FAIL detail now names both possible causes and points at the one thing that actually disambiguates them (the App's Installed repositories list on GitHub).

## App has no `logging.basicConfig`: every `logger.info(...)` in the codebase is silently never emitted in production
- **When:** Same session, Phase 0 — tried to verify the webhook allowlist's drop path (`_enqueue_from_payload`'s `logger.info("Ignoring webhook for non-target repo %s", ...)`) via Render logs, as agreed with the user beforehand.
- **What happened:** Queried Render's Logs API (`GET /v1/logs`, text-filtered for that exact message) after a webhook for a non-allowlisted repo had definitely been delivered and dropped (confirmed independently via an empty `tickets` table). Got back `{"logs": null}` — no match, ever. Root cause: nothing in the codebase calls `logging.basicConfig` (or otherwise configures the root logger's level), and the Dockerfile's `uvicorn` invocation (`CMD ["uv", "run", "--no-dev", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]`) passes no `--log-level` flag either. Worked around by using ticket-table presence/absence as the verification signal instead (`_enqueue_from_payload`'s allowlist check runs before any ticket write, so a dropped webhook simply never creates a row) — a strictly better signal for that specific question, but it doesn't generalize to other things INFO-level logging exists to surface (dispatcher activity, retry/backoff decisions, etc.), which remain invisible in production regardless.
- **Cost:** None to this session's actual test goals (the DB-based workaround was sufficient and arguably more authoritative). - **Suggested CLAUDE.md/code change:** Made (2026-08-17, follow-up session `fix-deploy-multi-repo`, commit `bdd7690`) — `app/main.py` now calls `logging.basicConfig(level=logging.INFO, force=True)` at module level. On the deliberate-default question: INFO was judged safe given actual volume — at the time of this fix there was exactly one `logger.info()` call in the whole codebase (the webhook-drop line), firing only for a webhook on a repo outside the allowlist, not per-request traffic.

## A requested security + code review of the whole onboarding wizard found a real SSRF vulnerability in the Vertex credential frame, plus 9 correctness bugs — all fixed in one pass

- **When:** 2026-08-28, user-requested "a set of reviews of the entire onboarding app" — a `security-review`-skill pass (diffed against `origin/main`, i.e. the wizard's whole build) and a `code-review`-skill pass (`onboarding/`, high effort), run in parallel, independently of the task-scoped reviews that already passed each sub-project.

One flagged item (a claim that a real Supabase project ref could contain a digit, defeating the router's `^[a-z]{20}$` validator) was checked against Supabase CLI's own upstream source (`ProjectRefPattern = regexp.MustCompile(`^[a-z]{20}$`)`) and confirmed a **false positive** — the existing code was already correct; left untouched rather than "fixed."

Every external-API-shape assumption made while fixing the correctness bugs (UptimeRobot's create/list/delete response shapes, its pagination field) was verified against UptimeRobot's own published OpenAPI spec before being written into code, not guessed — consistent with `[[feedback-verify-live-api-struct-before-plan]]`, extended here to "verify via published docs," not just "verify via a live call," when a live call isn't available/appropriate.
- **Suggested CLAUDE.md change:** Worth generalizing explicitly: **a credential-accepting endpoint that constructs an auth/HTTP client object from a visitor-supplied structured value (JSON, a config blob) needs a specific SSRF-focused check during its own design/review — does any field in that structure influence which host a server-side request is made to? — not just the "returns a verdict, never the credential" review this project already does well.** That specific class of gap (a "paste your service-account JSON" feature routing internal fields into a client library that reads them for connection-destination purposes) is exactly the shape a task-scoped review focused on credential *handling* (never logged, never echoed) can miss, because the vulnerable field isn't the credential itself — it's inert-looking routing metadata sitting right next to it in the same JSON blob.

The generalisable rule: **when a value is something the runtime can observe directly, do not also accept it as configuration** — a hand-set copy of a self-evident fact is not redundancy, it is a second source of truth that can only drift. This project already had the better pattern elsewhere (`bot/config.py` derives its own `public_base_url` from `RENDER_EXTERNAL_URL` rather than requiring it by hand); the onboarding service never picked it up, and the browser is a better authority still, since it is the party actually being redirected. ## Supabase's OAuth same-tab redirect reset the whole wizard's sessionStorage on mobile Firefox

- **When:** 2026-09-02, testing frame 5 (Supabase) after frames 1-4 completed successfully.
- **What happened:** After authorizing the wizard in Supabase's consent screen (mobile Firefox), the browser landed back on `/oauth/supabase/callback` with every frame — not just frame 5's pending OAuth state — showing as not-started, as if the visitor had opened a brand-new wizard session. Code review ruled out an application bug: no stray `sessionStorage.clear()`, no key collisions, the callback route serves byte-identical HTML to `/`, and `restoreFromSession()` runs correctly against whatever `sessionStorage` actually contains at load time. The leading explanation is a browser-level one: `connectSupabase()` used a same-tab `location.href` redirect to Supabase's authorize endpoint, and the consent screen can take long enough (login, MFA, review) that a mobile browser reclaims the tab's browsing context while it's backgrounded/away. Per spec, a recreated browsing context gets fresh, empty `sessionStorage` even though the origin and URL are unchanged on return — indistinguishable, from the page's own perspective, from a genuinely new session, since nothing in its JS ran incorrectly; the storage it depended on was simply gone before its code ever executed.
- **What's uncertain:** Whether this is specific to mobile Firefox, mobile browsers generally, or a narrower condition (e.g. only under memory pressure) — not independently reproduced across other browsers as part of this fix.
- **Fix:** `connectSupabase()` now opens the authorize URL in a popup (`window.open(..., "_blank")`) instead of redirecting the current tab, so this tab's `sessionStorage` is never at risk — it never navigates away at all. The popup does no work itself: it detects it's running inside a popup via `window.opener`, forwards `{code, state}` back to the opener with `postMessage` (targeted at this origin, and the opener validates both `event.origin` and `event.source` before trusting it), then closes. The opener — which still holds the pending PKCE verifier and every other frame's state — completes the actual token exchange. If the popup is blocked or folded into a same-tab navigation by the browser, it falls back to the original same-tab redirect, so the flow never breaks outright even where popups don't work. See `onboarding/CLAUDE.md`'s sub-project 3 section.
- **Cost:** One confusing-looking (but not data-destructive) reset during testing; no credentials were exposed or lost, since the visitor simply had to redo the affected frames. The larger cost was diagnostic: ruling out an application bug required a full code review of the OAuth callback path before landing on a browser-level explanation with no error message or diagnostic to confirm it.
- **Suggested CLAUDE.md change:** Recorded in `onboarding/CLAUDE.md`'s sub-project 3 section. Generalisable lesson: **`sessionStorage` is not guaranteed to survive a same-tab redirect to a third-party site and back**, even though the spec says navigation alone shouldn't clear it — a long enough trip away, especially on mobile, risks the browser reclaiming the tab's browsing context, which does reset it. A popup that never navigates the original tab away is a more robust pattern for any future external-redirect flow (installed once here; GitHub's App-creation and -install steps are already fully manual per the entries above, so this doesn't apply there today, but would be the pattern to reach for if that ever changes).

## The popup fix above didn't work: window.opener was severed by Supabase's own Cross-Origin-Opener-Policy

- **When:** 2026-09-02, testing the popup fix from the entry immediately above.
- **What happened:** The popup opened correctly and the visitor could authorize in it, but the popup then redirected to what looked like a brand-new wizard session instead of closing, while the original tab stayed stuck on "checking…" until the popup was closed by hand (at which point frame 5 reset to its start state). No Supabase project was created. Root cause: `handleSupabaseOauthCallback()` decided whether it was running inside the popup by checking `window.opener`, but Supabase's own authorize/login pages send `Cross-Origin-Opener-Policy: same-origin` — a deliberate, increasingly common anti-tabnabbing default many OAuth providers use — which permanently severs `window.opener` for a popup the moment it navigates there. By the time the popup returned to this app's own origin, `window.opener` was `null`, so the popup fell through to the "no opener" branch and treated itself as an ordinary standalone tab. Since a popup is a brand-new browsing context, its `sessionStorage` never held the pending PKCE state `connectSupabase()` wrote in the *original* tab — so `completeSupabaseOAuth()` immediately failed its own `!pending` check and surfaced `err_supabase_callback_invalid`, doing nothing further. That failure, on a tab with none of frames 1-4's state either, is what looked like "a reset wizard." The original tab, meanwhile, never received a `postMessage` (nothing was ever sent) and just sat waiting until its `popup.closed` poll eventually fired.
- **Fix:** Replaced both mechanisms this bug touched. Popup detection no longer uses `window.opener` at all — `handleSupabaseOauthCallback()` instead checks whether *this tab's own* `sessionStorage` holds the pending state: absence reliably means "this is the popup" (a fresh tab never has it), regardless of COOP. Cross-tab handoff moved from `window.opener.postMessage` to a shared-name `BroadcastChannel` (`SUPABASE_OAUTH_CHANNEL_NAME`), which only requires same-origin, not an opener relationship, so COOP severance can't affect it either. See `onboarding/CLAUDE.md`'s sub-project 3 section for the corrected design.
- **Cost:** A second round of live testing to catch what the first popup fix's own testing hadn't exercised (only "does the popup open" was checked, not "does the round trip actually reach the opener"); no credentials or account consequences.
- **Suggested CLAUDE.md change:** Recorded in `onboarding/CLAUDE.md`'s sub-project 3 section (the same bullet the prior entry added, corrected in place rather than appended twice, since it now describes the actual shipped mechanism). Generalisable lesson: **`window.opener` cannot be assumed to survive a popup navigating to a third-party origin** — an increasing number of sites (deliberately, for tabnabbing protection) send `Cross-Origin-Opener-Policy: same-origin`, which severs it permanently for that browsing context. Any future popup-based flow should use `BroadcastChannel` (or, if payload size/broadcast semantics don't fit, a dedicated relay endpoint) for the handoff instead of relying on `window.opener`, and should verify the *full* round trip live (popup opens **and** the result actually reaches the opener), not just that the popup opens.

## The stateless-relay invariant itself was the root cause — replaced with a server-side session, not patched around again

- **When:** 2026-09-02, immediately after the `BroadcastChannel` fix above (still unconfirmed by the user's own retest) and a follow-up brainstorm.
- **What happened:** Before the user could even retest the `BroadcastChannel` fix, a walkthrough of the redirect-and-resume design surfaced that a same-tab redirect (needed to replace the popup, since a plain cookie-based session would make the popup entirely unnecessary) would still lose the *rest* of the wizard's progress on the same mobile browsers that motivated all three entries above — because `sessionStorage` itself, not just the OAuth leg's pending state, is what gets wiped when a mobile browser reclaims a backgrounded tab's browsing context. Every fix so far (popup, then `BroadcastChannel`) treated the symptom at the Supabase-OAuth call site specifically; none addressed that the wizard's *only* place to keep state was exactly the browser storage mechanism found to be unreliable.
- **Root cause:** `onboarding/CLAUDE.md`'s stated invariant — "this backend is a stateless relay... must never gain a database, a session store" — was a deliberate architectural choice made before any of the three mobile incidents above occurred, on the assumption that `sessionStorage` was durable enough to survive the wizard's several full-page redirects. It wasn't. The invariant itself, not any one call site's handling of it, was the thing that needed to change.
- **Fix:** Replaced the stateless-relay design with a server-side session (`onboarding/session_store.py`) in a new, dedicated Postgres, identified by an `HttpOnly`/`Secure`/`SameSite=Lax` cookie — cookies are part of the browser's persistent cookie jar, not tied to a specific browsing-context instance, so they survive the tab reclamation that broke `sessionStorage`. Every credential is application-encrypted (Fernet) before being written. This let the Supabase OAuth leg return to a plain same-tab redirect with no popup/`BroadcastChannel`/`window.opener` machinery at all — the callback route completes the exchange purely server-side. See
  `docs/superpowers/specs/2026-09-01-onboarding-server-side-session-design.md` (design, including the fork/resurrection-risk hardening on `update_frame()` found during design review) and
  `docs/superpowers/plans/2026-09-02-onboarding-server-side-session.md` (16-task implementation plan, executed inline in the same session). `onboarding/CLAUDE.md`'s invariant section and sub-project 3/6 sections were rewritten to match; the popup/`BroadcastChannel` design the two entries above shipped is deleted, not deprecated.
- **Cost:** A full architectural rebuild touching every credential-bearing endpoint (~20) and the whole frontend credential-storage/restore path — substantially larger than any single fix above, but this is the first fix in this chain that addresses the actual root cause rather than the latest place it surfaced.
- **Suggested CLAUDE.md change:** Recorded directly in `onboarding/CLAUDE.md`'s invariant section (rewritten in place, not appended). Generalisable lesson: **when the same class of failure resurfaces after two consecutive fixes at the same call site, stop fixing that call site and ask whether the surrounding architecture itself is what's fragile.** Both the popup and `BroadcastChannel` fixes were reasonable, well-tested responses to what looked like local bugs; neither would have been the right amount of effort if the real problem had been named up front. The trigger that should prompt this check is: two-plus fixes at the same site, each addressing a symptom the previous fix didn't anticipate.

## A requested correctness review of the whole onboarding wizard, right after the server-side session rewrite, found a CRITICAL page-breaking bug and 7 more real correctness bugs — all fixed in one pass

- **When:** 2026-09-02, immediately after the server-side session persistence rewrite (see the entry above), user-requested "a code-correctness reviewer on a highly capable model to review the entire onboarding sub-project." One `general-purpose`/Opus subagent, given the design spec, the implementation plan, and every file under `onboarding/` (backend and the full inline frontend `<script>`), instructed to focus exclusively on correctness (not style/simplification).
- **What happened:** The review found 8 real issues, most severe first:
  1. **CRITICAL:** `applyLanguage()` (called from every page load, before `restoreFromSession()`) called `document.getElementById("github-app-name-input")` — an element removed from the DOM by the 2026-09-01 manual-GitHub-App-flow redesign, over a week before this session's own work. Every single page load threw a `TypeError` at that line and silently aborted the rest of `DOMContentLoaded`, meaning **`restoreFromSession()` — the entire point of this session's rewrite — never ran on any page load, ever**, along with the theme toggle and the new "Start over" listeners. Undetected until now because every existing test in this project's convention is a content-substring check against served HTML/JS, not a JS execution harness — nothing before this review actually *ran* the script.
  2. Supabase's `/api/session` completeness gate keyed off `ref` (written by `create-project`) rather than `database_url` (written much later by `connection-info`, after the ~2 minute provisioning poll) — a reload during that wait would falsely report the frame complete, unlock the next frame, and reach deploy with no `DATABASE_URL` to push, silently.
  3. `restoreFromSession()`'s render-service local-storage write was a full replace, not a merge — on an ordinary same-tab reload (not even the mobile tab-discard case this rewrite targets), it silently destroyed `pending_deploy_id`/`deployed`, breaking deploy-status resume and enabling a duplicate-deploy click.
  4. The UptimeRobot Main API key was still being written to `sessionStorage` and resent in `/api/uptimerobot/delete-monitor`'s request body — the one remaining credential this rewrite's own stated invariant ("no credential touches sessionStorage") didn't actually cover.
  5. `supabase_client.py`'s carried-forward diagnostic `print()` had a fallback branch that could `repr()` a raw, unvalidated Supabase API response — which may carry `db_host`/`connection_string` — into the logs, if that response was ever a single object instead of a list.
  6. `beginChange()` only ever cleared the browser's local mirror, never the server-side session — resubmitting a different Render key, or reconnecting Supabase, left the *previous* account's `service_id`/`ref`/`database_url` sitting in the session for a reload to resurrect or a later step to reuse against the wrong account/project.
  7. Every `session_store.py` call in `router.py` ran synchronously on the request coroutine despite `session_store.py`'s own module docstring stating (and the design spec confirming) that callers must run it via `asyncio.to_thread` — every request blocked the single event loop for the duration of its own Postgres round-trips.
  8. `update_frame()`'s `SessionNotFound` return value was ignored at every call site, and the function never checked whether its own `UPDATE` actually affected a row — a session deleted in the gap between an endpoint's session check and its write (TTL expiry, a concurrent reset) silently reported success while persisting nothing.
  All eight were independently verified against the actual code (not taken on the review's word) before fixing. Fixes: removed the stale `getElementById` call and added a blanket regression test (`test_every_getelementbyid_target_exists_in_the_markup`) scanning every `getElementById("...")` in the page against every `id="..."` in the markup — the only test in this file capable of catching this whole class of bug; changed the Supabase completeness gate to require `database_url`, adding a new resumable "provisioning" (ref-but-no-database_url) state that resumes polling instead of falsely completing; changed the render-service restore write to merge onto the existing local mirror instead of replacing it; moved the UptimeRobot API key into the server-side session and made `delete-monitor` session-backed with no body, matching every other post-redesign endpoint; narrowed the diagnostic's fallback to a type name / dict-key-names-only summary, never a value repr; added a `replace=True` option to `update_frame()` for the two endpoints (`validate-key`, `connect`) that represent "start this frame over," so a resubmission discards the previous account/project's stale fields outright instead of merging onto them; wrapped every `session_store` call in `router.py` in `asyncio.to_thread` via small internal wrapper functions; and added a rowcount check to `update_frame()`'s own `UPDATE`, plus explicit `SessionNotFound` handling at every call site where an unpersisted "success" would otherwise be reported as real (deliberately left unchecked at the one site — `trigger-deploy`'s `pending_deploy_id` write — where the external side effect, a real deploy, is already irreversible and non-idempotent, so failing the response would only invite a duplicate-deploy retry).
- **Cost:** None net-negative — caught by a review requested immediately after the rewrite, before any deployment or user retest. But #1 alone is a reminder that this project's whole test suite for `onboarding/static/index.html` cannot catch a JS runtime error by construction (content-substring checks never execute the script), and had been blind to a page-breaking bug for over a week; the new blanket `getElementById` test only guards this one class of failure, not JS correctness generally.
- **Suggested CLAUDE.md change:** Worth generalizing: **content-substring tests against served HTML/JS (this project's established pattern for single-file static pages) can never catch a runtime error, only a missing/wrong string.** The new `test_every_getelementbyid_target_exists_in_the_markup` closes the specific `getElementById`-on-a-removed-element gap generally (not just for the one bug that surfaced it) and should be treated as a standing regression guard, not a one-off fix — any future removal of an element referenced elsewhere in the script is now caught automatically. A real JS execution/DOM harness would catch strictly more (any runtime error, not just this one pattern) but is a bigger investment than this project's static-page convention has called for so far.

### Supabase OAuth app is a shared resource across all visitors — abuse or Supabase's own heuristics can throttle/revoke it for everyone
- **Found during:** sub-project 3 (Supabase provisioning) brainstorm, 2026-08-26
- **What:** the planned Supabase frame authorizes every visitor through one operator-registered OAuth app (`SUPABASE_OAUTH_CLIENT_ID`/`SUPABASE_OAUTH_CLIENT_SECRET`). Unlike the Render frame (each visitor's own key) or the GitHub frame (each visitor mints their own App), this credential is a single shared identity across the whole visitor population.
- **Why it matters:** same risk category as the documented Gemini AI-Studio Trust & Safety block (root `CLAUDE.md`'s "LLM API testing hygiene" section) — a burst of activity from one visitor, or Supabase's own abuse heuristics, could throttle or revoke the shared app's Management API access, breaking the Supabase frame for every future visitor until re-registered, not just the one who triggered it.
- **Status:** open
- **Follow-up:** design a countermeasure before or shortly after this frame reaches real visitors. Candidates raised during brainstorming: per-visitor rate limiting at this service's own layer, a CAPTCHA/friction step before the OAuth redirect, or active monitoring for revocation with a clear "this frame is temporarily down" fallback state. Not solved in sub-project 3's spec or plan — deliberately deferred.

### Supabase OAuth App registration's plan-tier availability is undocumented
- **Found during:** sub-project 3 (Supabase provisioning) brainstorm, 2026-08-26
- **What:** no Supabase documentation (pricing page, billing FAQ, the "Build a Supabase Integration" guide) states whether registering an OAuth App (organization settings → OAuth Apps tab) requires a paid org plan, or costs anything at all. Searched directly across all three; the absence is the finding — it's simply never addressed either way.
- **Why it matters:** this project is committed to $0 demo cost (root `CLAUDE.md`'s Cost section, `cost.md`). If OAuth Apps require a paid organization tier, sub-project 3's design dependency on one would break that constraint.
- **Status:** needs-verification
- **Follow-up:** the operator confirms this directly when manually registering the OAuth app — a one-time, deliberate dashboard action sub-project 3's design already requires. No purchase happens automatically or by surprise, since that registration step is manual and operator-initiated, not something the wizard or any automation triggers.

### Dashboard "Environment" feature (fetch/modify Render env vars + config DB) parked pending dashboard authentication
- **Found during:** brainstorming session, 2026-08-28
- **What:** sketch so far, captured before the brainstorm paused to redirect at authentication — a new expandable side menu on the dashboard page (`app/static/dashboard.html`) with two items: **Status** (today's existing content — stats, queue, reviews — moved under this item unchanged) and **Environment** (new).
